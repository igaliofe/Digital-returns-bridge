תכנון ראשוני לפרויקט בסדנה בתכנות מתקדם ב-JAVA Digital Returns Bridge — מערכת לניהול החזרות מוצרים במרלו"ג

עיצוב המסכים מבוסס על קובץ Figma: Digital Returns Bridge — Screen Designs (24 מסכים).

1. תיאור המערכת מבחינה פונקציונלית

המערכת המוצעת היא מערכת לניהול תהליך החזרות מוצרים במרכז לוגיסטי. מטרת המערכת היא ליצור תהליך דיגיטלי רציף בין מחלקת השירות, הנהגים בשטח, צוות המחסן והניהול הלוגיסטי.

המערכת תאפשר פתיחת קריאת החזרה דיגיטלית באמצעות אשף שלוש שלבים (זיהוי לקוח → בחירת פריט מהיסטוריית רכישות → פרטי החזרה), הקצאת הקריאה לנהג, העלאת תמונות וחתימות, ועדכון מצב האיסוף על ידי הנהג. בזמן האיסוף, הנהג ידביק על המוצר מדבקה עם ברקוד פנוי שאינו משויך, יסרוק את הברקוד באפליקציית Android, והמערכת תשייך את הברקוד לקריאת ההחזרה. בעת הגעת המוצר למחסן, המחסנאי יסרוק או יזין את הברקוד — בממשק Web או באפליקציית Android — ויקבל את תיק ההחזרה הדיגיטלי המלא.

המערכת אינה מנהלת מאגר ברקודים או pool של ברקודים. הברקודים קיימים כמדבקות פיזיות אצל הנהג, והמערכת מכירה ברקוד רק לאחר שהנהג סורק אותו ומשייך אותו לקריאת החזרה קיימת.

במערכת יהיו ארבעה סוגי משתמשים:

  • נציג שירות
  • נהג / מוביל
  • מחסנאי / עובד מרלו"ג
  • מנהל מערכת / מנהל לוגיסטי

1.1 נציג שירות

נציג השירות ישתמש בממשק Web מבוסס JSF, מעוצב לפי Figma.

הפעולות המרכזיות של נציג השירות במערכת:

  • התחברות למערכת באמצעות מספר טלפון.
  • יצירת קריאת החזרה חדשה באמצעות אשף שלוש שלבים:
    • שלב 1 — זיהוי לקוח: חיפוש לקוח לפי מספר טלפון.
    • שלב 2 — בחירת פריט: בחירת פריט מתוך היסטוריית רכישות הלקוח. פריטים שכבר טופלו (נפתחה עבורם קריאת החזרה) יוצגו כלא-נבחרים.
    • שלב 3 — קריאה חדשה: השלמת פרטי ההחזרה — צ'קליסט (תאריך מסירה, כמות, אחריות, שימוש, סיבת החזרה, פרטי פגם), הערות, עדיפות, שיוך נהג, תמונות כלליות ופגם, וחתימת נציג שירות.
  • שמירת הקריאה בסטטוס WAITING_FOR_PICKUP.
  • צפייה ברשימת קריאות, בפרטי קריאה ובדשבורד.
  • צפייה בברקוד המשויך לקריאה לאחר שהנהג סרק אותו בשטח.
  • צפייה בהיסטוריית הטיפול בקריאה.

1.2 נהג / מוביל

הנהג ישתמש באפליקציית Android בזמן האיסוף מהלקוח.

הפעולות המרכזיות של הנהג במערכת:

  • התחברות לאפליקציה באמצעות מספר טלפון.
  • צפייה ברשימת האיסופים שהוקצו לו (שם לקוח, כתובת, מוצר, סטטוס איסוף וסטטוס ברקוד).
  • צפייה בפרטי איסוף: פרטי לקוח, כתובת, מוצר, תמונת קטלוג, סיבת החזרה וציר זמן.
  • הדבקת מדבקה עם ברקוד פנוי על המוצר בבית הלקוח.
  • סריקת הברקוד (מצלמה או הזנה ידנית) ושיוכו לקריאת ההחזרה.
  • צילום הפריט (תמונת מוצר, תמונה ממרחק, תמונת פגם — תמונת פגם חובה).
  • אישור איסוף: סימון מצב הפריט, פרטי פגם, הערות נהג וחתימת נהג.
  • שליחת הנתונים, הברקוד, התמונות והחתימה לשרת.

1.3 מחסנאי / עובד מרלו"ג

המחסנאי ישתמש בשני ערוצים: ממשק Web מבוסס JSF ואפליקציית Android בעת קליטת המוצרים במחסן. אותה אפליקציית מובייל תשרת גם נהגים וגם מחסנאים, ולאחר ההתחברות המערכת תנתב את המשתמש למסכים המתאימים לתפקידו.

הפעולות המרכזיות של המחסנאי במערכת:

  • התחברות למערכת באמצעות מספר טלפון.
  • צפייה בתור עבודה של פריטים שנאספו (PICKED_UP) ושל פריטים שהגיעו למחסן (ARRIVED_TO_WAREHOUSE).
  • סריקה (באמצעות מצלמת האפליקציה) או הזנה ידנית של הברקוד המודבק על המוצר.
  • שליפת תיק ההחזרה הדיגיטלי לפי הברקוד.
  • צפייה בפרטי הלקוח והמוצר, מק"ט, תיאור, תמונת קטלוג ומחיר.
  • צפייה בסיבת ההחזרה, בפרטי הפגם ובתמונות שהועלו על ידי נציג השירות והנהג.
  • צפייה במצב הפריט, בפרטי הפגם ובהערות הנהג.
  • סימון פריט כהגיע למחסן (קליטת מחסן).
  • בקשת מידע נוסף מהנהג / השירות כאשר המידע אינו מספיק (סטטוס NEEDS_MORE_INFO).
  • בדיקת מחסן: סיווג מצב הפריט, קביעת אופן הטיפול בו, והחלטה האם הקריאה טופלה במלואה.
  • הוספת הערות מחסן.
  • סימון "טופל במלואו" לסגירת הקריאה (סטטוס CLOSED).
  • צפייה בהיסטוריית הטיפול בקריאה.

1.4 מנהל מערכת / מנהל לוגיסטי

המנהל ישתמש בממשק Web מבוסס JSF.

הפעולות המרכזיות של המנהל במערכת:

  • התחברות למערכת באמצעות מספר טלפון.
  • צפייה בכל קריאות ההחזרה, עם אפשרות סינון לפי סטטוס, נהג, לקוח או תאריך.
  • צפייה בדשבורד עם מדדי ביצוע (KPI): קריאות פתוחות, ממתינות לאיסוף, עם ברקוד משויך, שנאספו, במחסן, נסגרו, ועם מידע חסר.
  • צפייה בדוחות מפורטים (כולל פריטים שנבדקו במחסן).
  • ניהול משתמשים, לקוחות, מוצרים ונהגים.

2.1 JSF - JavaServer Faces

JSF ישמש לבניית ממשק ה-Web של המערכת. המסכים המתוכננים:

  • מסך התחברות.
  • Dashboard.
  • אשף פתיחת קריאת החזרה (3 שלבים: זיהוי לקוח, בחירת פריט, קריאה חדשה).
  • מסך רשימת קריאות החזרה.
  • מסך פרטי קריאת החזרה.
  • מסך קליטת מחסן.
  • מסך דוחות.
  • מסכי ניהול נתוני מערכת (משתמשים, לקוחות, מוצרים, נהגים).

2.2 Android

אפליקציית ה-Android היא אפליקציה רב-תפקידית המשרתת גם נהגים וגם מחסנאים. לאחר ההתחברות, האפליקציה תבדוק את תפקיד המשתמש ותנתב אותו למסכים המתאימים.

זרימת נהג: התחברות → רשימת איסופים → פרטי איסוף → שיוך ברקוד → צילום תמונות → אישור איסוף (כולל חתימה).

זרימת מחסנאי: התחברות → תור עבודה → סריקת ברקוד → תיק החזרה → בדיקת מחסן והחלטה.

2.3 JPA - Java Persistence API

JPA ישמש למיפוי מחלקות Java לטבלאות בבסיס הנתונים. הישויות המתוכננות:

  • User
  • Customer
  • CustomerPurchase
  • Product
  • Driver
  • ReturnRequest
  • ReturnImage
  • PickupUpdate
  • WarehouseInspection
  • StatusHistory

2.4 REST Web Services

REST Web Services ישמשו לחשיפת פעולות השרת עבור אפליקציית Android ועבור פעולות המערכת. השרת יחשוף קריאות לניהול התחברות, משתמשים, לקוחות (כולל היסטוריית רכישות), מוצרים, נהגים, קריאות החזרה, שיוך ברקוד, העלאת תמונות, עדכוני איסוף, קליטת מחסן ודוחות.

2.5 Cloudinary

Cloudinary ישמש לשמירת תמונות המועלות למערכת מממשק ה-JSF (נציג שירות) ומאפליקציית Android (נהג). בבסיס הנתונים יישמרו פרטי התמונה: כתובת, מזהה ב-Cloudinary, סוג התמונה, המשתמש שהעלה, קריאת ההחזרה המשויכת ותאריך העלאה.

3. ארכיטקטורה ורכיבי המערכת העיקריים

המערכת תיבנה בארכיטקטורת שכבות, כאשר יש שני סוגי לקוחות: ממשק Web פנימי מבוסס JSF עבור נציג השירות, המחסנאי והמנהל, ואפליקציית Android רב-תפקידית עבור הנהגים והמחסנאים בשטח.

אפליקציית ה-Android אינה ניגשת ישירות לבסיס הנתונים, אלא מתקשרת עם השרת באמצעות REST API. בצד השרת תהיה שכבת לוגיקה עסקית משותפת, שכבת גישה לנתונים (Repository) ורכיב ייעודי להעלאת תמונות ל-Cloudinary.

5.1 מסך התחברות

מסך התחברות משותף למשתמשי ה-Web וה-Android. ההתחברות תתבצע באמצעות מספר טלפון בלבד. לאחר ההתחברות, המערכת תנתב את המשתמש למסך המתאים לפי תפקידו.

5.2 Dashboard

מסך ראשי עבור נציג שירות, מחסנאי ומנהל. יציג 8 כרטיסי KPI: קריאות פתוחות, ממתינות לאיסוף, עם ברקוד משויך, שנאספו, במחסן, נסגרו, עם מידע חסר, וללא ברקוד. פעולות: מעבר לרשימת קריאות, פתיחת קריאה חדשה, מעבר לדוחות.

5.3 אשף פתיחת קריאת החזרה (3 שלבים)

מסך עבור נציג שירות.

שלב 1 — זיהוי לקוח: חיפוש לקוח לפי מספר טלפון.

שלב 2 — בחירת פריט: טבלת היסטוריית רכישות (מוצר, מספר הזמנה, כמות, תאריך מסירה, אחריות). פריטים שכבר טופלו מסומנים ואינם ניתנים לבחירה.

שלב 3 — קריאה חדשה: פרטים ממולאים מראש מהרכישה. שדות: שימוש בפריט, סיבת החזרה, פרטי פגם, הערות, עדיפות, שיוך נהג, תמונות, וחתימת נציג שירות. שמירה תיצור קריאה ללא ברקוד ותסמן את הרכישה כ"טופלה".

5.4 מסך רשימת קריאות החזרה

מסך עבור נציג שירות, מחסנאי ומנהל. מציג: ברקוד (אם שויך), שם לקוח, מוצר, סטטוס, נהג, תאריך פתיחה, עדיפות. אפשרות סינון לפי סטטוס, נהג, לקוח וחיפוש לפי ברקוד.

5.5 מסך פרטי קריאת החזרה

מציג את כל פרטי הקריאה: לקוח ומוצר (כולל תמונת קטלוג), ברקוד, תמונות (כולל חתימות), פרטי איסוף נהג, מצב פריט, הערות, סטטוס, היסטוריה וציר זמן.

5.6 מסכי Android — נהג

רשימת איסופים: שם לקוח, כתובת, מוצר × כמות, צ'יפ סטטוס, צ'יפ ברקוד.

פרטי איסוף: פרטי לקוח, כתובת, מוצר, תמונת קטלוג, ברקוד, ציר זמן. פעולות: שיוך ברקוד, צילום, אישור איסוף.

שיוך ברקוד: סריקה (מצלמה) או הזנה ידנית.

צילום תמונות: תמונת מוצר, תמונה ממרחק, תמונת פגם (חובה).

אישור איסוף: מצב פריט, פרטי פגם, הערות, חתימת נהג.

5.7 מסך קליטת מחסן (Web)

מסך עבור המחסנאי בממשק ה-Web. סריקה/הזנת ברקוד, שליפת תיק החזרה, סימון "הגיע למחסן", בקשת מידע נוסף, וביצוע בדיקת מחסן.

5.8 מסכי Android — מחסנאי

תור עבודה: פריטים ב-PICKED_UP ו-ARRIVED_TO_WAREHOUSE, כפתור סריקה.

סריקת ברקוד: סריקה באמצעות מצלמת המכשיר, שליפת תיק ההחזרה.

תיק החזרה: פרטי ההחזרה המלאים, סימון "הגיע למחסן", כניסה לבדיקת מחסן.

בדיקת מחסן: תצוגת מידע לקריאה בלבד (פרטי מוצר, תמונות, פרטי פגם). שאלה "מספיק מידע?" — אם לא, בקשת מידע נוסף; אם כן, סיווג מצב הפריט, החלטת מחסן (מלאי / סיווג / תיקון / השמדה), וסימון "טופל במלואו" לסגירת הקריאה.

5.9 מסך דוחות / KPI

מסך עבור מנהל. 9 כרטיסי KPI (כולל פריטים שנבדקו), טבלאות וגרפים: החזרות לפי סטטוס, החלטות מחסן, מידע חסר, ביצועי נהגים, החזרות יומיות.

5.10 מסכי ניהול נתוני מערכת

מסכים עבור מנהל: ניהול משתמשים, לקוחות, מוצרים (כולל תמונת קטלוג) ונהגים. משתמשים, לקוחות ומוצרים — דרך REST API (או backing beans). נהגים — מסך ייעודי (DriverAdminBean): יצירת רשומת נהג על ידי שיוך User קיים (role=DRIVER) + פרטי רכב/טלפון; עדכון ומחיקה דרך שכבת השירות, לא דרך REST.

6. תיאור בסיס הנתונים

בסיס הנתונים יהיה בסיס נתונים רלציוני (PostgreSQL). הגישה אליו תתבצע באמצעות JPA. המערכת אינה כוללת טבלת ברקודים — הברקוד נשמר כשדה בקריאת ההחזרה, ורק לאחר סריקה בשטח.

6.1 טבלאות עיקריות

  • users — משתמשי המערכת (טלפון, שם, תפקיד, פעיל).
  • customers — לקוחות (שם, טלפון, כתובת, דוא"ל).
  • customer_purchases — היסטוריית רכישות (לקוח, מוצר, מספר הזמנה, כמות, תאריך מסירה, אחריות, דגל "טופל").
  • products — מוצרים (מק"ט, שם, קטגוריה, מחיר, תמונת קטלוג).
  • drivers — נהגים (משתמש, מספר רכב, טלפון).
  • return_requests — קריאות החזרה (לקוח, מוצר, רכישה, נהג, ברקוד, צ'קליסט, סטטוס, עדיפות).
  • return_images — תמונות (כתובת, סוג, מעלה, קריאה).
  • pickup_updates — עדכוני איסוף (מצב פריט, פרטי פגם, חתימת נהג, הערות).
  • warehouse_inspections — בדיקות מחסן (מצב פריט, החלטת מחסן, "טופל במלואו", הערות).
  • status_history — היסטוריית שינויי סטטוס.

6.2 דיאגרמת ERD (תמצית)

אין טבלת ברקודים — הברקוד הוא שדה ב-return_requests, nullable עד לסריקה בשטח.

7. תשתית והפעלה (High Level)

המערכת תופעל בסביבת פיתוח ובדיקות באמצעות Docker Compose. התשתית תכלול שני שירותים עיקריים:

  • בסיס נתונים — PostgreSQL 15, עם טעינה אוטומטית של סכמה ונתוני בדיקה בעת אתחול.
  • שרת אפליקציה — WildFly 30+ שמארח את אפליקציית Jakarta EE 10 (ממשק JSF + REST API + JPA).

אפליקציית ה-Android (נהגים ומחסנאים) אינה חלק מ-Docker — היא רצה על מכשיר/אמולטור ומתקשרת עם השרת ב-REST API. תמונות וחתימות יאוחסנו ב-Cloudinary (שירות חיצוני, חובה להגדרת credentials אמיתיים).
